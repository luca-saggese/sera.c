# M3 — Qwen3-32B Q4: Shared-Prefix KV + Batched Decisions on GB10

## 0. Obiettivo

M0 ha chiuso:

```text
GGUF
→ mmap
→ fast resident CUDA load
→ stable device pointers
```

M1 ha chiuso:

```text
resident Q4 weights
→ production quantized CUDA linear
```

M2 ha chiuso:

```text
token IDs
→ complete 64-layer Qwen3 forward
→ B1 KV cache
→ candidate logits
```

M3 deve trasformare questo runtime in un vero **decision engine multi-question**:

```text
STATE
  ↓
prefill UNA VOLTA
  ↓
immutable shared prefix KV
  ├── question 0 suffix
  ├── question 1 suffix
  ├── question 2 suffix
  ├── ...
  └── question B-1 suffix
           ↓
    ONE batched suffix forward
           ↓
    candidate logits [B,K]
```

Il problema da risolvere è quindi:

> stesso state, molte decisioni, senza ricomputare né duplicare fisicamente il prefix.

---

# 1. Hard target

Alla fine deve essere possibile fare concettualmente:

```c
q3_prefix *prefix = q3_prefix_create(
    runtime,
    state_tokens,
    state_count);

q3_decision_batch batch = {
    question_0,
    question_1,
    ...
};

q3_decide_batch(
    runtime,
    prefix,
    &batch,
    results);
```

ottenendo:

```text
result[0] → candidate logits + argmax
result[1] → candidate logits + argmax
...
result[B-1]
```

senza:

```text
re-prefill state B volte
copy prefix KV B volte
generation
autoregressive decoding
full vocabulary logits
```

---

# 2. Scope M3

M3 include:

```text
shared immutable prefix KV

branch-local suffix KV

prefix/suffix KV view

B=1,2,4,8,16,32

batched suffix forward

variable suffix lengths

batched Q4 linear reuse

batched attention over:
    shared prefix
    +
    private suffix

candidate logits per branch

memory accounting

performance benchmark

correctness against M2
```

M3 NON include:

```text
custom trained decision head

continuous batching across unrelated requests

generic paged attention engine

vLLM-style scheduler

prefix eviction policy

prefix cache database

cross-request automatic prefix matching

generation

sampling

server

multi-GPU

CUDA Graphs

speculative decoding
```

M3 risolve il nostro caso specifico:

```text
ONE state
→ MANY decisions
```

---

# 3. Non costruire un generic KV system

Non implementare una cache general-purpose.

La struttura necessaria è molto più semplice:

```text
immutable shared prefix
        +
private append-only suffix per branch
```

Modello concettuale:

```text
                    ┌────────────────────┐
                    │ shared prefix KV   │
                    │ positions 0..P-1   │
                    └──────────┬─────────┘
                               │
             ┌─────────────────┼─────────────────┐
             │                 │                 │
             ▼                 ▼                 ▼
       branch 0          branch 1          branch 2
       suffix KV         suffix KV         suffix KV

       P..P+S0-1         P..P+S1-1         P..P+S2-1
```

Il prefix deve esistere **una volta fisicamente**.

M3 non deve correggere problemi numerici lasciati aperti da M2.

# 7. KV geometry

Per il target Qwen3:

```text
layers = 64
KV heads = 8
head dim = 128
```

Ogni token richiede per layer:

```text
K: 8 × 128
V: 8 × 128
```

Il datatype effettivo è quello già scelto e validato in M2.

Calcolare e riportare esplicitamente:

```text
KV bytes/token/layer
KV bytes/token/model
```

Non usare stime sparse nel codice.

Avere helper unico:

```c
q3_kv_bytes_for_tokens(...)
```

# 8. Prefix object

Creare un oggetto esplicito:

```c
typedef struct {
    uint32_t token_count;

    void *layer_k[Q3_LAYERS];
    void *layer_v[Q3_LAYERS];

    size_t capacity_tokens;
    size_t bytes;

    uint64_t generation;
    bool sealed;
} q3_prefix_kv;
```

La struttura esatta può differire.

Concetti obbligatori:

```text
owned storage
immutable after sealing
known token count
known capacity
stable device pointers
```

Una volta completato il prefill:

```text
prefix->sealed = true
```

e nessuna domanda deve modificarlo.

---

# 9. Prefix lifecycle

API concettuale:

```c
q3_prefix_kv_create(...)
q3_prefix_kv_prefill(...)
q3_prefix_kv_seal(...)
q3_prefix_kv_destroy(...)
```

Oppure equivalente coerente col runtime esistente.

Il prefill deve eseguire:

```text
state tokens
→ M2 forward
→ write K/V directly into prefix storage
```

Non:

```text
temporary KV
→ memcpy into prefix
```

se il layout M2 consente di evitarlo.

# 10. Branch object

Ogni domanda deve possedere solo il proprio suffix state:

```c
typedef struct {
    const q3_prefix_kv *prefix;

    uint32_t suffix_tokens;
    uint32_t suffix_capacity;

    void *suffix_k[Q3_LAYERS];
    void *suffix_v[Q3_LAYERS];
} q3_kv_branch;
```

Il branch:

```text
references prefix
owns suffix
```

Non:

```text
owns a copy of prefix
```


# 12. Logical KV view

L'attention di una branch deve vedere logicamente:

```text
[ shared prefix | private suffix ]
```

senza richiedere che siano fisicamente contigui.

Creare una view semplice:

```c
typedef struct {
    const void *prefix_k;
    const void *prefix_v;
    uint32_t prefix_count;

    const void *suffix_k;
    const void *suffix_v;
    uint32_t suffix_count;
} q3_kv_view;
```

eventualmente per layer.

Non costruire una generic scatter/gather abstraction.

Sono sempre al massimo due segmenti:

```text
segment 0 = shared prefix
segment 1 = private suffix
```

# 16. Variable suffix lengths

Le domande non avranno tutte la stessa lunghezza.

Non obbligare semanticamente ogni suffix ad avere la stessa lunghezza.

Il batch deve conoscere:

```text
suffix_lengths[B]
```

Padding interno è ammesso se il kernel lo richiede.

Ma:

```text
padding tokens
```

non devono:

```text
modify KV
participate in attention
produce candidate output
```

---

# 17. Position IDs

Per branch `b`:

```text
global_position =
    prefix_tokens +
    suffix_local_position
```

Questo deve essere indipendente dal padding del batch.

Non derivare le positions da:

```text
physical tensor column
```

se esiste left/right padding.

Creare explicit position metadata se necessario.

---

# 18. Batched embedding

Input:

```text
B suffix sequences
```

deve diventare una singola operazione/batched set di operazioni.

Non fare:

```c
for (b = 0; b < B; ++b)
    full_forward(branch[b]);
```

M3 non è completa se implementa soltanto un loop B1.

Il loop CPU può preparare descriptors.

Il compute principale deve essere batched.

---

# 19. Batched linear

Riutilizzare il backend M1/M2.

L'obiettivo è trasformare:

```text
B independent suffix matrices
```

in un input compatto che consenta al Q4 backend di vedere un M più grande.

Concettualmente:

```text
total active suffix tokens = Σ S_b
```

e per ogni layer:

```text
Q4 linear over active tokens
```

piuttosto che:

```text
B separate Q4 kernel chains
```

quando possibile.

---

# 20. Packed active-token representation

Preferire un layout concettuale:

```text
packed_hidden:
    branch0 token0
    branch0 token1
    ...
    branch1 token0
    ...
```

con side arrays:

```text
token_to_branch[]
token_local_position[]
branch_offsets[]
branch_lengths[]
```

Questo permette:

```text
one RMSNorm
one Q projection
one K projection
one V projection
...
```

su tutti i token attivi.

Non costruire un generic ragged-tensor framework.

Solo gli array necessari.

---

# 21. Attention resta branch-aware

Le projection possono lavorare sul packed token matrix.

Attention invece deve sapere:

```text
a quale branch appartiene ogni query
```

per leggere:

```text
same shared prefix
+
that branch private suffix only
```

Una query della branch 3 non deve mai vedere suffix K/V della branch 4.

---

# 22. Suffix KV layout

Preferire storage:

```text
[layer][branch][position][kv_head][head_dim]
```

oppure equivalente che renda efficiente il kernel scelto.

Non scegliere layout soltanto per comodità host.

La decisione deve essere basata sul kernel attention M2/M3.

Documentarla in:

```text
docs/research/m3/04_final_kv_layout.md
```

Questo è l'unico documento di design aggiuntivo consentito durante implementation.

Deve essere corto.

---

# 23. KV allocation strategy

Per il benchmark M3 conosciamo:

```text
B max = 32
suffix max length
```

Quindi per M3 è accettabile:

```text
allocate suffix arena once
for maximum configured capacity
```

Non serve paged allocation.

Pattern:

```text
one shared prefix arena
+
one suffix arena
```

o poche allocation grandi.

Non:

```text
cudaMalloc per layer per branch
```

---

# 24. No 64×32 allocation explosion

Hot runtime non deve avere:

```text
64 layers × 32 branches × K/V allocations
```

come oggetti CUDA separati.

Usare grandi arena con offsets.

Esempio concettuale:

```text
prefix_arena
suffix_arena
workspace_arena
```

con pointer arithmetic precomputed.

# 46. Batch success criterion

Il production M3 path deve avere compute sostanzialmente strutturato come:

```text

    operations over packed active suffix tokens

    attention branch-aware
```

non:

```text

    run M2 layer stack
```

Un eventuale branch loop dentro un piccolo attention component può essere temporaneamente accettabile se il bulk delle Q4 projection è realmente batched.

# 74. Definition of Done

M3 è completa quando:

```text
1. Uno state viene prefetched una sola volta.

2. Il prefix KV viene memorizzato una sola volta fisicamente.

3. Il prefix diventa immutable/sealed.

4. È possibile creare B branch senza copiare il prefix.

5. Ogni branch possiede solo suffix KV privato.

6. L'attention legge:
       shared prefix
       +
       correct private suffix.

7. Nessuna branch può leggere il suffix di un'altra.

8. I suffix vengono processati realmente in batch.

9. Funzionano:
       B=1
       B=2
       B=4
       B=8
       B=16
       B=32.

10. Variable suffix lengths funzionano correttamente.

11. Candidate logits vengono prodotti per ogni branch.

12. B32 produce gli stessi argmax delle 32 esecuzioni M2 individuali.

13. prefix_copy_bytes == 0.

14. prefix physical KV bytes non crescono con B.

15. Dopo warmup:
       unexpected CUDA allocations == 0
       unexpected host syncs == 0.

16. Esistono benchmark:
       B1/B2/B4/B8/B16/B32.

17. Esistono smoke:
       ~2K prefix B8
       ~8K prefix B8
       se la memoria lo consente.

18. Massimo quattro test M3.

19. Gli artifact sono salvati.

20. Il benchmark dimostra throughput migliore rispetto al loop di forward indipendenti.
```

Quando tutto questo è vero:

# COMMIT E STOP.

Non implementare automaticamente server, continuous batching o custom head.

La milestone successiva può concentrarsi su uno dei due rami, in base ai numeri M3:

```text
A. ottimizzazione performance del runtime
```

oppure:

```text
B. custom decision head / calibration
```

ma la decisione va presa solo dopo avere i risultati B1…B32 reali.
