# M1 — Qwen3-32B Q4: quantized linear compute on GB10

## 0. Obiettivo

M0 ha costruito:

```text
Q4 GGUF
   ↓
mmap
   ↓
tensor descriptors
   ↓
residency plan
   ↓
fast CUDA resident load
   ↓
stable device pointers
```

M1 deve aggiungere **il primo primitive di calcolo reale** sopra quei resident pointers:

```text
resident Q4_K matrix
        +
device activation matrix
        ↓
Q4_K quantized linear
        ↓
device output
```

con:

```text
correctness
+
batch support
+
performance measurements
```

La milestone deve terminare quando possiamo eseguire una **vera projection matrix del Qwen3-32B Q4 GGUF** direttamente dal formato quantizzato residente, senza dequantizzare persistentemente i pesi.

## Hard STOP

```text

RoPE

```

M1 è esclusivamente:

# 9. Matrix semantics

Usare una convenzione unica:

```text
weight = [N, K]
input  = [M, K]
output = [M, N]
```

dove:

```text
M = token_count
K = input features
N = output features
```

Non dipendere implicitamente dall'ordine delle dimensioni GGUF.

Il binder deve convertire una volta:

```text
GGUF physical dims
→
logical N,K
```

e validarlo.

Il kernel riceve geometry già risolta.

---

# 10. Input activation

Per M1 l'API esterna usa:

```text
FP32 device activation
```

per semplicità e perché il donor q38 usa già float activation in numerosi primitive.

Questo **non congela** l'activation ABI finale del runtime.

Se il donor Q4 CUDA scelto richiede internamente:

```text
Q8_1 activations
```

allora copiare anche il donor activation quantization path.

Pipeline ammessa:

```text
FP32 activation
    ↓
device Q8_1 quantization
    ↓
Q4_K × Q8_1 quantized GEMM
    ↓
FP32 output
```

Questo è preferibile a dequantizzare i pesi.

---


---

# 12. Due execution regimes

Il workload futuro ha sia:

```text
single/few token suffix
```

sia:

```text
multi-token prefill
```

Quindi M1 deve validare entrambi.

Il backend può avere due path interni:

```text
M == 1
→ MMV / MMVQ

M > 1
→ MMQ / quantized batched GEMM
```

Se il donor scelto usa una soglia diversa, mantenere inizialmente la sua logica.

Non inventare tuning threshold in M1.

Prima copiare la dispatch donor e misurare.

---

# 13. No naive generic production fallback

Il vecchio-style kernel:

```text
one CUDA output element
→ scalar loop over every K
→ dequant one weight at a time
```

può restare come:

```text
debug fallback
test oracle
```

ma non deve essere chiamato silenziosamente dal production backend.

Se il production Q4 kernel non supporta una geometry:

```text
FAIL LOUDLY
```

M1 deve seguire la filosofia q38:

```text
no silent slow fallback
```

---

# 14. Workspace

Qualunque workspace richiesto da:

```text
activation quantization
MMQ tiles
temporary Q8_1 activation
```

deve essere:

```text
allocated once
reused
grown only when necessary
```

Non:

```text
cudaMalloc every linear call
cudaFree every linear call
```

Dopo warmup:

```text
cuda_allocations_per_linear == 0
```

---

# 15. Synchronization

Il production Q4 linear primitive non deve chiamare:

```text
cudaDeviceSynchronize
cudaStreamSynchronize
cudaEventSynchronize
```

come parte normale del compute.

Ordine tramite:

```text
same CUDA stream
```

Il benchmark harness può sincronizzare per misurare il kernel.

Il primitive no.

Target:

```text
host_syncs_per_linear == 0
```

---

# 16. Correctness oracle

Usare il Q4_K CPU implementation copiato da q38 come oracle principale.

Per una matrix reale:

```text
resident Q4_K weight
```

preparare deterministicamente un piccolo input.

Esempio:

```text
sin/cos deterministic values
fixed PRNG seed
no random_device
```

Reference:

```text
Q4_K CPU dequant
+
FP32 dot product
```

GPU:

```text
Q4_K production kernel
```

Confrontare:

```text
max_abs_error
mean_abs_error
RMSE
cosine similarity
top-k largest absolute errors
```

Se il production donor quantizza l'activation in Q8_1, non pretendere bit-exact equality con FP32 reference.

Stabilire la tolerance dai numeri reali.

Non scegliere una tolerance enorme semplicemente per far passare il test.

Salvare i numeri.

# 22. Performance decision

Non fissare prima un target artificiale come:

```text
must be < X ms
```

Prima misurare.

Ma M1 **non è completa** se il backend accepted è chiaramente un scalar/debug kernel.

Deve essere un vero quantized CUDA path con:

```text
cooperative weight decoding
vectorized quantized dot products
weight reuse where appropriate
batched kernel for prefill
```

Se il kernel è numericamente corretto ma molto lento:

1. profilare;
2. identificare la causa concreta;
3. correggere solo quella;
4. rifare i 4 benchmark.

Non iniziare il full forward per “vedere comunque quanto va”.

# 30. Definition of Done

M1 è completa quando:

```text
1. un vero tensor Q4_K del Qwen3 GGUF
   viene usato direttamente dal resident device pointer;

2. non esiste un persistent dequantized weight mirror;

3. M=1 usa un production quantized CUDA path;

4. M>1 usa un production batched quantized CUDA path;

5. il risultato è validato contro il CPU Q4 oracle;

6. repeated hot calls fanno:
      cuda_allocations == 0
      host_syncs == 0

7. esistono benchmark GB10 per:
      M=1
      M=4
      M=16
      M=32

8. esistono:
      docs/research/m1/*
      artifacts/m1_q4/correctness.json
      artifacts/m1_q4/bench.json
      artifacts/m1_q4/summary.md

9. massimo tre test M1 passano.

10. il codice production deriva chiaramente da donor copiati,
    rinominati e adattati, non da una nuova implementazione ad hoc.
```

A questo punto:

# STOP.
